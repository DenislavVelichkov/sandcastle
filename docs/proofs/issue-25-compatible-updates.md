## Operations and results

Two roots were installed from the first GitHub release and registered in one isolated inventory. The npm root's repeated current-release plan and apply returned `current` without rewriting it. Both roots retained their generated entry, custom prompt, custom hook and owner policy. The pnpm root ran the installed controller to a durable waiting request. Its request identity and remaining iteration count (`0`) stayed unchanged through rollout; status remained readable, and the owner-route fixture queued a response without applying it or starting a model.

The selected npm root's first update injected a worker verification failure after package apply. Its journal and activation block prevented a new run. Rollback restored the first release's installed bytes and cleared the block only after verification. A subsequent compatible update installed the second release. A concurrent owner edit to `package.json` caused rollback to refuse the edit and leave the root blocked for inspection. Restoring the updater's expected bytes allowed rollback to restore the first release. These failures used disposable roots; no saved state or custom file was reset.

An explicit two-root rollout to the second release reported `updated` for npm and `deferred` for the pending pnpm root. Repeating the same rollout reported `current` and `deferred`. After deliberately changing npm's managed entry, the selected rollout reported `failed` and `deferred` without changing the pnpm root or rolling npm back globally. Restoring the entry allowed selected verification to pass. Inventory records include canonical installation, project, worktree and package-workspace identities, last verified readiness time, rollback availability and recovery owner. After update, installation and model-fixture checks were `verified`; controller, browser, native and human-response readiness remained `unverified`.

The guide's CLI `list`, `inspect --tag v0.12.0-dv8.22.0`, and `plan --tag v0.12.0-dv8.22.0` operations were repeated against the final disposable inventory. They reported two registered roots, `current` with a verified tag, and an idempotent `current` plan. The update, rollback, verify and selected rollout calls in the retained proof use the same exported transaction and inventory functions as those CLI commands.
